# חוזה ה-API

> מתעדכן **באותו קומיט** של כל שינוי בנקודות הקצה. חוזה לא מעודכן = ממצא 🟠 HIGH.
>
> **הכלל:** רכיב ממשק לעולם אינו ניגש לדאטהבייס. כל תקשורת עוברת דרך `/api/*`
> ודרך `lib/api/client.ts` בלבד. זו השכבה היחידה שתוחלף כשנעבור ל-React Native.

## GET /api/health

בדיקת תקינות סביבה **ובדיקת סכמה חיה**. משמשת גם את סוכן ה-Critic כדי לזהות סביבה שגויה,
ואת בדיקת העשן שאחרי כל קידום (`plan/RULES.md` § 0.1 ד׳).

**תגובה — 200 כשתקין, 503 כשלא:**

```json
{
  "ok": true,
  "checks": [
    { "name": "supabase_url",                "ok": true, "detail": "configured" },
    { "name": "supabase_anon_key",           "ok": true, "detail": "configured" },
    { "name": "placeholder_content_blocked", "ok": true, "detail": "blocked" },
    { "name": "database_schema",             "ok": true, "detail": "word_progress reachable" }
  ]
}
```

`placeholder_content_blocked` נכשל כאשר `NEXT_PUBLIC_ALLOW_PLACEHOLDER=true` —
כלומר תוכן לימודי לא מאומת חשוף למשתמשים. זהו מצב אסור ב-production.

**ENV תקין אינו מספיק: `ok:true` מחייב שהמיגרציות הורצו.** `database_schema` מריץ
`select` על `word_progress` עם `head:true` — הוא אינו קורא אף שורה של אף לומד, ואפס
שורות תחת RLS הן **הצלחה** (הן מוכיחות ש-PostgREST ענה ושהטבלה קיימת). ⛔ מחרוזת
השגיאה הגולמית של Supabase לעולם אינה נכנסת ל-JSON; `detail` מוגבל לארבע המחרוזות:

| מצב | `detail` |
|---|---|
| הטבלה נגישה | `word_progress reachable` |
| קוד שגיאה `42P01` / `PGRST205` | `word_progress missing — migrations not applied` |
| כל שגיאה אחרת, חריגה, או timeout (3 שניות) | `database unreachable` |
| אין ENV של Supabase — לא נוסתה בדיקה כלל | `not probed — supabase env missing` |

## POST /api/auth/signup

יצירת חשבון. **גוף הבקשה:** `{ "email": string, "password": string }`

**200 — הצלחה:**

```json
{ "ok": true, "outcome": "session_active", "next": "/onboarding", "email": "roy@example.com" }
```

`outcome` הוא `session_active` כשהתקבל session (אימות אימייל כבוי ב-Supabase),
או `awaiting_email_confirmation` כשנשלח מייל אישור ואין session. אז `next` הוא
`/login`. הקוד תומך בשתי ההגדרות ואינו מניח אף אחת מהן — ראה `docs/SETUP.md` נספח ב-2.

**422 — כשל ולידציה מקומי:** `{ "ok": false, "fieldErrors": { "email"?: string, "password"?: string } }`
**409 — האימייל תפוס:** `{ "ok": false, "code": "email_taken", "message": "...", "email": "..." }`
**429 — חריגה מהגבלת הקצב:** `{ "ok": false, "code": "rate_limited", "message": "..." }`
עם כותרת `Retry-After` בשניות. שתי מכסות נבדקות וההחלטה המחמירה מנצחת:
**10 הרשמות ל-10 דקות לכל כתובת IP** ו-**3 הרשמות לשעה לכל כתובת אימייל**.
המכסה לפי IP היא זו שסוגרת את התרחיש של F-008 — תוקף שמריץ 100 אלף כתובות
צריך מולה כ-69 ימים במקום דקות. המכסה לפי אימייל מכוונת מעל כל ניסיון כן
(לומד שהקליד שגוי פעמיים עדיין נכנס) ומתחת לאוטומציה.
**400 / 503 — אחר:** `{ "ok": false, "code": "...", "message": "..." }`
**400 — גוף בקשה שאינו אובייקט** (`null`, מערך, מחרוזת, מספר): `{ "ok": false, "code": "unavailable", "message": "..." }`.
חל על שני נתיבי האימות. הגוף `null` עובר את `request.json()` בלי לזרוק, ולפני F-004
הפיל את הנתיב ל-500 עם stack trace בלוג. הגנה: `isCredentialPayload` ב-`lib/core/auth.ts`.

בהצלחה עם session נוצרת גם שורת `profiles` עם `track_id='amiram'` (D-016).
המקור הסמכותי ליצירתה הוא טריגר בדאטהבייס (`supabase/migrations/0001_profiles.sql`);
הכתיבה מכאן היא רשת ביטחון לפרויקט שהמיגרציה טרם הורצה בו.

## POST /api/auth/login

התחברות. **גוף הבקשה:** `{ "email": string, "password": string }`

**200:** `{ "ok": true, "next": "/onboarding" }`
**401:** `{ "ok": false, "code": "invalid_credentials", "message": "אימייל או סיסמה שגויים" }`
**429:** `{ "ok": false, "code": "rate_limited", "message": "..." }`
עם כותרת `Retry-After` בשניות. ⚠️ **השורה הזו הייתה בחוזה לפני שהיה לה מייצר** —
עד C-0160 רק ספק האימות יכול היה להחזיר 429, והאפליקציה רק העבירה אותו הלאה.
מעכשיו המגבלה היא **שלנו**: **20 התחברויות ל-10 דקות לכל IP** ו-**8 לרבע שעה לכל
כתובת אימייל**. המכסה לפי IP רופפת מזו של ההרשמה בכוונה — כיתה שלמה מאחורי NAT
אחד היא מקרה אמיתי, ונעילת הכיתה כדי להאט תוקף היא העסקה הגרועה יותר.
**400:** גוף בקשה שאינו אובייקט — זהה ל-signup לעיל (F-004).

⛔ **כל כשל אימות מוחזר עם אותה הודעה בדיוק.** "המשתמש לא קיים" הופך את נקודת
הקצה לכלי למיפוי משתמשים רשומים.

## POST /logout

פעולה, לא מסך (תוכנית UX של T-002). נשלחת מ-`<form method="post">` רגיל, כך
שהיציאה עובדת גם בלי JavaScript ולא ניתנת להפעלה על ידי תגית `<img>` זרה כמו
יציאה מבוססת GET. מסתיימת **תמיד** ב-`303`, גם אם ה-signOut נכשל.

מקבלת שדה טופס יחיד ואופציונלי, `destination`. הערך היחיד שיש לו משמעות הוא
`fix_address` (T-026) — יציאה שנועדה לתקן כתובת שגויה, שמסתיימת ב-`303` ל-
`/signup?email=<הכתובת שהייתה בסשן>`. **כל** ערך אחר, לרבות נתיב או כתובת מלאה,
מסתיים ב-`303` ל-`/` — הגוף מגיע מבקשה לא מאומתת, ולכן הוא אסימון ולא יעד.

## שדות משותפים לכל נקודות הקצה של האימות

* `message` הוא **תמיד עברית מוכנה להצגה**. קוד שגיאה גולמי או טקסט אנגלי של
  הספק לעולם לא מגיע ללומד — אותו כלל מ-T-001. המיפוי ב-`lib/core/auth.ts`.
* ה-session נשמר ב-cookies מסוג httpOnly שנכתבים על ידי `@supabase/ssr`.
  **לא ב-`localStorage`** — שם כל סקריפט שהוזרק יכול לקרוא אותו.
  ⚠️ `@supabase/ssr` **אינו** מספק את זה כברירת מחדל (`httpOnly: false`, בלי `secure`).
  ההבטחה הזו מתקיימת אך ורק דרך `SESSION_COOKIE_OPTIONS` ב-`lib/supabase/auth.ts`,
  שמועבר כ-`cookieOptions` לכל קריאת `createServerClient`. `secure` דולק בפרודקשן בלבד,
  אחרת `http://localhost` היה מפיל את העוגייה בפיתוח. F-002 — מכוסה בבדיקת יחידה.
* `proxy.ts` **נכשל סגור**: כשחסרים משתני הסביבה של Supabase, נתיב מוגן מופנה ל-`/login`
  ואינו נפתח. בנוסף `app/onboarding/page.tsx` בודק `getUser()` בעצמו — הפרוקסי אינו
  עוד נקודת האכיפה היחידה. F-003.
* רענון ה-session והשמירה על הנתיבים המוגנים מתבצעים ב-`proxy.ts` (שם הקונבנציה
  של Next 16; `middleware` הוצא משימוש).

## GET /api/profile

המטרה של הלומד ומניין המילים שלמד — הקריאה שהלשונית `אני` הייתה עושה **בשרת** עד
T-334 (`36 § 13` · `T-328`). דורש סשן חי.

🔬 **למה הנתיב הזה קיים, ⛔ ולא כשיפור סגנוני:** `npm run build` סימן `○ /cards` ·
`○ /world` · `○ /settings` · `○ /studies` מול **`ƒ /me`** — ארבע לשוניות מתוך חמש
הוגשו מהקצה, והחמישית עשתה הלוך-ושוב לשרת **ול-Supabase** בכל מעבר, לפני שצויר
פיקסל אחד. ⇒ הקריאה עברה לכאן, ו-`<MeScreen>` שולף אותה בעצמו דרך `apiGet` —
בדיוק הדפוס של `GET /api/levels/summary`.

**שתי הקריאות רצות ב-`Promise.all`, ⛔ ולא בזו אחר זו:** שתיהן תלויות ב-`user.id`
בלבד, וזו שורת **השהיה** — שני `await` עוקבים היו מחזירים את מרבית מה שהמעבר הרוויח.

**200 — נקרא:**

```json
{
  "ok": true,
  "goal": { "institution": null, "targetScore": 120, "examDate": "2026-09-10" },
  "wordsLearned": 189,
  "dailyMinutes": 10
}
```

🆕 **`dailyMinutes` (T-352)** — `5 | 10 | 20 | null`, **מחוץ** ל-`goal` כי הלשונית ⛔ אינה
מציגה אותו. הוא נוסע כדי שעדכון תאריך מבחן שעבר (`<MeExamDateUpdate>` בלשונית `אני`)
יוכל לבנות גוף ש-`POST /api/profile` מקבל — `checkOnboarding` דורש אותו. ⛔ אין נתיב
חדש ו⛔ אין שינוי סכמה: העדכון שולח את שלוש התשובות, ושתיים מהן חוזרות כפי שנקראו.

`goal` הוא שלוש התשובות של ה-Onboarding **בדיוק כפי שנשמרו** — ⛔ אין חישוב עליהן
(‏4.4.3). כל שדה `nullable`, כי כל אחד מהם אופציונלי בטופס, ו-`null` נקרא «לא ענה»
⛔ ולא «אפס». `institution` ⛔ אינו נכתב עוד (D-056 · T-111) ו**נקרא** כאן, עבור
לומדים שענו לפני ההסרה.

🔴 **`wordsLearned` הוא `number | null`, ושתי האפשרויות הן שתי עובדות שונות:**
`0` הוא לומד שטרם למד מילה, ו-`null` הוא **קריאה שנכשלה**. קיפולן לאחת הוא שקר על
המסך (T-301), ולכן `count ?? 0` חל **אך ורק** על ענף ההצלחה. `<MeWordsLearned>`
מצייר משפט עברי ו«נסה שוב» עבור `null`, ומספר עבור `0`.
⚠️ **ומצב שלישי חי בצד הלקוח ו⛔ לא כאן:** «בדרך». הנתיב ⛔ אינו מחזיר אותו — הוא
היעדר תשובה, ו-`<MeScreen>` מצייר עבורו את `<MeWordsLearnedSkeleton>`.

⛔ **מניין המילים הוא `mastered_at is not null`, ⛔ ולא ספירת שורות `word_progress`:**
«למד» הוא שליטה (D-010 · `lib/core/progress.ts`), וספירת כל שורה הייתה מדווחת על
מילה שנראתה פעם אחת כמילה שנלמדה. השליפה היא `head: true` ⇒ ⛔ אפס שורות על החוט.

**401 — אין סשן:** `{ "ok": false, "code": "session_expired" }`
**503 — הסכמה חסרה:** `{ "ok": false, "code": "schema_missing", "message": "המאגר עדיין לא הוקם" }`
**503 — סביבה לא מוגדרת:** `{ "ok": false, "code": "unavailable" }`

⚠️ **`schema_missing` הוא של קריאת הפרופיל בלבד, וזו א-סימטריה מכוונת:** לקריאת
המניין **יש** כבר תשובה גלויה ללומד (`wordsLearned: null`), בעוד שקריאת פרופיל
שנכשלה מצטיירת כ**היעדר בלוק מטרה** — שתיקה כנה עבור כשל רגעי, ו**שקר** כשהעמודה
אינה קיימת. `42703` (‏`undefined column`) הוא המצב הצפוי עד שמיגרציה רצה בייצור,
בדיוק כמו ב-`GET /api/levels/summary`.

⚠️ **הסשן נבדק כאן, ⛔ ולא רק ב-`proxy.ts`** — לקח F-003, ששני מנעולים יושבים על
**שתי דלתות שונות**. `getUser()` שישב ב-`app/(tabs)/me/page.tsx` ⛔ לא היה המנעול
השני אלא **שלישי על אותה דלת**, והוא היה הקריאה לשרת עצמה.

## POST /api/profile

שמירת תשובות ה-Onboarding על שורת הפרופיל של הלומד (T-029 · פרוסת ההתמדה של T-003).
דורש סשן חי — הבדיקה נעשית **לפני** ולידציה של הגוף, כדי שקורא לא מאומת לא ילמד
אילו שדות מתקבלים.

**גוף הבקשה:**

```json
{ "dailyMinutes": 5, "examDate": "2026-09-10", "targetScore": "" }
```

**מה קרה לשדה `institution`:** השאלה **הוסרה** — D-056 · T-111 (הוראת רוי, 19/08).
מפתח `institution` בגוף בקשה **מתקבל ונופל לרצפה** ⛔ ואינו 422, כדי שלומד שעמוד
ישן שלו נשאר פתוח בדפדפן יוכל לשמור. ⛔ **העמודה `profiles.institution` נשארת**
(`0009_onboarding_institution.sql`, nullable) ונקראת ב-`/me` בלבד, עבור לומדים
שענו לפני ההסרה — ⛔ אין `drop column`.

`examDate` ו-`targetScore` ריקים (`""`) פירושם "דילג" ונשמרים כ-`NULL`.
`dailyMinutes` חייב להיות אחד מ-`5 | 10 | 20` (‏`DAILY_MINUTES_OPTIONS` ב-
`lib/core/onboarding.ts`), ואותה שלישייה נאכפת שוב במסד דרך
`profiles_daily_minutes_check` ב-`0004_onboarding_answers.sql`. בדיקת יחידה
נכשלת אם השתיים נפרדות.

⚠️ **"היום" הוא היום בלוח השנה של הלומד, לא של השרת.** ולידציית `examDate` מקבלת
`toIsoDateInZone(new Date(), LEARNER_TIME_ZONE)`. ישראל היא UTC+2/+3, ולכן
בשעתיים-שלוש הראשונות של כל יום מקומי `new Date().toISOString()` עדיין מחזיר את
תאריך **אתמול** — לומד שממלא את הטופס אחרי חצות ביום המבחן היה יכול לשמור תאריך
שכבר עבר (C-0032).

**200 — נשמר:**

```json
{ "ok": true, "next": "/studies" }
```

`next` הוא היעד היחיד שנקבע כאן: `components/OnboardingForm.tsx` מנווט למה שמגיע
בשדה הזה ואינו מחזיק יעד משלו. **C-0073: השתנה מ-`/study` ל-`/studies`** לפי
§ 4.2ב זרימה 1 — `/study` הוא מסך זרימה בלי סרגל לשוניות, ולומד שנחת בו לא יכול
היה להגיע לשלוש הלשוניות האחרות בלי לערוך את כתובת ה-URL.
`app/api/profile/route.test.ts` נכשלת אם המחרוזת כאן והמחרוזת בקוד נפרדות.

**422 — שדה לא תקין.** כל השדות הפגומים מדווחים יחד, לא הראשון בלבד:

```json
{ "ok": false, "fieldErrors": { "examDate": "התאריך הזה כבר עבר." } }
```

**401 — אין סשן:** `{ "ok": false, "code": "session_expired" }`
**400 — גוף שאינו אובייקט** (`null`, מערך, פרימיטיב — F-004): `{ "ok": false, "code": "unavailable" }`
**503 — סביבה לא מוגדרת או כתיבה נכשלה:** `{ "ok": false, "code": "unavailable" }`

הכתיבה היא `update` ולא `upsert`: הטריגר `on_auth_user_created` ב-
`0001_profiles.sql` כבר יצר את השורה, ו-`upsert` היה נאלץ לחזור על `track_id` —
מקום שני שבו ברירת המחדל חיה הוא מקום שני שבו היא יכולה להיות שגויה (D-016).

## POST /api/review

תשובה אחת על כרטיס אחד: צבירת ההתקדמות (T-005 · טלמטריית D-010) **וגם** תזמון
החזרה הבאה (מנוע 7.1). דורש סשן חי — הבדיקה נעשית **לפני** קריאת הגוף, כדי שקורא
לא מאומת לא ילמד אילו שדות מתקבלים.

**גוף הבקשה:**

```json
{
  "word_id": "11111111-2222-3333-4444-555555555555",
  "grade": "good",
  "direction": "recognition",
  "elapsed_ms": 4200
}
```

`grade` חייב להיות אחד מ-`BINARY_GRADES` ו-`direction` אחד מ-`CARD_DIRECTIONS`,
ושניהם **מיובאים** מ-`lib/core/flashcard.ts` ולא משוכפלים כאן — הכרטיס מציע בדיוק
את הדירוגים שה-API מקבל, ובדיקה נכשלת אם השניים נפרדים.

⚠️ **`elapsed_ms` חסום ב-`MAX_ELAPSED_MS = 600000` (10 דקות) ונדחה ב-400 מעל זה,
לא נחתך בשקט.** לומד שהשאיר כרטיס פתוח לילה שלם היה כותב `time_to_first_correct`
בן שמונה שעות אל תוך השדה היחיד שכל שכבת הטלמטריה של D-010 קיימת בשבילו; ערך
שנחתך ל-600000 אינו ניתן להבחנה מערך אמיתי.

מוחרג מאותה סיבה בכיוון ההפוך: הוא השדה שמקדם מילה לייצור (7.7), ותרגול חוזר על

ומוודא שהם נעדרים.

חסרה נשארת 404: מילה בלי שורת התקדמות מעולם לא נענתה, ומילה שמעולם לא נענתה אינה
יכולה להיות בחפיסות אלו.

🔓 **T-225 · D-142 — התשובה 404 על מילה בלי שורת `word_progress` הצטמצמה:** היא
נשארת על כל חפיסה **חוץ מ-`deck=level` ומ-`deck=sentences`** (T-199ⓐ). חפיסת הרמה היא
**בהגדרה** אוסף המילים שטרם נענו, וחפיסת המשפטים נשלפת **מאותה שאילתת רמה בדיוק**

המסלול פותח שורה: «ידעתי» ⇒ `self_marked_known: true` · `attempts: 0`; «לא ידעתי» ⇒
`self_marked_known: false` · `attempts: 1` · **`next_review_at: null`**.
🔒 **`null` ⛔ אינו «מועד עכשיו»** — `deck=due` מסנן `next_review_at <= now`, ולכן
השורה ⛔ לעולם אינה נכנסת לחפיסת החזרה בטעות. ⛔ אפס SM-2 בשני המסלולים.

**401 — אין סשן:** `{ "ok": false, "code": "session_expired" }`

⛔ מחרוזת השגיאה של Supabase יוצאת ל-`console.error` בלבד ואינה נכנסת לגוף התשובה.

## GET /api/study/queue

תור הכרטיסיות — **החוליה שחיברה בין `Flashcard.tsx` ל-SM-2** (T-064 · D-032). דורש סשן
חי, והבדיקה נעשית **לפני** קריאת ה-query string, כדי שקורא לא מאומת לא ילמד אילו חפיסות

ואז `headword` — ⛔ ולעולם לא `senses.cefr_level`** (D-034: השניים חלוקים על 125 מתוך 343
משמעויות שנמדדו). רמה שאינה מוכרת אינה מנוחשת — היא שוקעת לסוף התור בדיוק כמו NULL.

פגום הוא באג ולא הגנה. משפט חסר ⇒ מחרוזת ריקה, והכרטיס נבנה בלעדיו.
`PROMOTE_AFTER_CONSECUTIVE_CORRECT = 3` הוא קבוע **במסלול** ועובר כארגומנט מדיניות ל-
`directionFor` — ⛔ הוא פרמטר מוצר ואינו ראיה, ולכן אינו חי ב-`/lib/core`.

   לברירת המחדל ונרשם ב-`console.error`.
2. `planDailyQueue({dueReviewCount, newCardsPerDay: NEW_CARDS_PER_DAY, dailyMinutesGoal,
   secondsPerCard: SECONDS_PER_CARD})` — הבלם מ-`lib/core/queue.ts` הוא שמחליט כמה חזרות
   וכמה מילים חדשות נכנסות היום, ⛔ ולא מספר קשיח במסלול. `NEW_CARDS_PER_DAY = 5` ו-
   `SECONDS_PER_CARD = 20` הם **פרמטרי מוצר** (`HEURISTIC`), ⛔ אינם ראיה פדגוגית, ⛔ ואינם

3. המועמדים נשלפים מ-`words` בסדר `cefr_profile_band` עולה (NULL בסוף) ואז `ngsl_rank`
   עולה — רמה, ואז תדירות. מילה שהלומד כבר פגש מסוננת ב-`excludeSeen` **בשכבה הטהורה**,

4. **המילים החדשות מצטרפות אחרי שורות החזרה** — חוב שכבר קיים קודם למילה שטרם נפגשה,

5. **כשל בשליפת המילים החדשות ⛔ אינו מפיל את התור** — הלומד מקבל את שורות החזרה,

6. ⚠️ **תקרה מתועדת:** מעל `MAX_SEEN_ROWS = 1000` שורות התקדמות, רשימת ה"כבר נפגשו" עלולה

   ידועה כחדשה. החזרות ממשיכות לזרום. רשום כחוב טכני ב-`plan/30-architecture.md`.

`total` בחפיסת `due` הוא **תור היום** — החזרות שקיבולת היום סופגת, בתוספת המילים החדשות,

### «סינון מילים» — `deck=level` (C-0318 · T-155 · D-089)

⛔ **החפיסה הזאת שואלת את `words`, ⛔ ולא את `word_progress`** — וזו כל הסיבה שהיא קיימת:

   ⛔ ולא מי רשאי, וכל רמה שיש בה מילים פתוחה לכל לומד.

   בענף הזה: התשובה ⛔ אינה תלויה ברמת הלומד, ולכן ⛔ אינה משלמת עליה.
1. בהיעדר `?band=` נקרא `profiles.current_level`. **`null` ⇒ `409` עם

3. ⛔ **אפס `excludeSeen`.** מילה שהלומד כבר פגש ⛔ אינה מסוננת: היא ברמה, והחפיסה היא

4. ⛔ **הדירוג ⛔ אינו נוגע ב-SM-2.** בדיוק כמו `unknown`: `applyPractice` מזיז `attempts`
   ו-`correct_attempts` בלבד (D-032 · D-033). **צפייה ⛔ אינה חשיפה שנענתה.**

`total` הוא מספר השורות **אחרי** מסנן החפיסה ו**לפני** החיתוך ל-`limit` — אותו כלל בדיוק

ו⛔ אינו משכפל אותו.

⚠️ **שני הספים חיים במסלול, לא בשכבה הטהורה:** `MIN_FUNCTION_WORDS = 100` ו-
`MIN_ACTIVE_WORDS = 12` הם **פרמטרי מוצר** (`HEURISTIC`) ועוברים כארגומנט מדיניות. D-031
קובעת במפורש ש-12 נמדד מ-403 המשפטים המאושרים שלנו (חציון 10 מילים), ⛔ אין לו מקור
פדגוגי ו⛔ אין לכתוב אותו ל-`plan/10-pedagogy.md`. שינוי כל אחד מהם ⛔ אינו דורש מיגרציה.

⚠️ **`functionWords` הוא מספר ה־headwords הייחודיים, ⛔ ולא מספר השורות.** ‏`words` הוא
`unique (headword, pos)`, ולכן אותה מילה מחזיקה כמה שורות וספירת שורות **מנפחת** את
המאגר (נמדד C-0092: 121 headwords על פני 139 משמעויות). PostgREST אינו יודע לבטא
`count(distinct headword)`, ולכן המסלול שולף את עמודת ה־headword תחת תקרה קשיחה של
`MAX_BANK_ROWS = 2000` וה-dedupe נעשה ב-`uniqueHeadwords` בשכבה הטהורה. ⛔ ספירת
`head: true` הייתה מדווחת שורות ו⛔ לא מילים.

`activeWords` נספר מ-`word_progress.is_active_this_week = true`, **מצומצם לקורא בלבד**
(`user_id = user.id`) — ⛔ אין כאן ספירה גלובלית.

⚠️ **גם `activeWords` הוא headwords מובחנים, ⛔ ולא שורות — תוקן ב-C-0126 (F-040).** עד
אז השדה נלקח מ-`count: 'exact', head: true`, כלומר **שורות** `word_progress`, והטבלה היא
**פר-סנס**: לומד שמחזיק את שני הסנסים של `can` נספר כשתי מילים במקום אחת. כיוון השגיאה
הוא תמיד ניפוח (`count ≥ distinct`), ולכן השער נפתח **מוקדם** — לפני שהלומד יודע
`MIN_ACTIVE_WORDS` מילים מובחנות. הקריאה היום היא `words!inner(headword)` תחת
`MAX_BANK_ROWS`, ועוברת באותו `uniqueHeadwords` שמשרת את `functionWords` — **אותה הגדרה
של «אותה מילה» בשני צדי הפרדיקט**, וזהה ל-`GET /api/world/bank`. ⚠️ טרנקציה בתקרה
מסוגלת רק **להקטין** לומד שכבר רחוק מעל הסף, ו⛔ לעולם לא לפתוח את השער מוקדם.

⚠️ **`stories` — האריח «הספרייה», וקריאה **רכה** (T-137ⓒ · § 4.2יג · D-074ⓑ).** כל תשובת
`ok:true` נושאת `stories: { required, atLevel } | null`:

* `required` — `STORIES_PER_LEVEL` (‏`lib/core/storyGate.ts`), ⛔ **ולא קבוע שני**: § 4.2יג
  נוקבת ב«≥3 סיפורים ברמת הלומד», וזה אותו מספר של מכסת הייצור ומאותו טעם.
* `atLevel` — כמה סיפורים יש **ברמת הלומד** (`profiles.current_level`). ⛔ `null` ⇒ ללומד
  עוד אין רמה, והוא ⛔ **אינו נחסם**: האריח פתוח ומוביל לסריקת הרמה (T-082).
* `stories: null` — הקריאה **נכשלה**. ⛔ זה ⛔ אינו «אפס סיפורים»: האריח מצייר «—».

⚠️ **הכישלון כאן ⛔ אינו 503, וזו הכרעה שנמדדה ⛔ ולא נוחות.** `0018_stories.sql` טרם הורץ
בייצור, ו-`<TabBar>` נועל את הלשונית על **כל** תשובה שאינה `ok:true` — כלומר קריאה קשיחה
הייתה נועלת את «העולם» לכל הלומדים עד שהמיגרציה תרוץ. ⇒ שתי הקריאות הישנות (הבנק והלומד)
⛔ **לא נגעו** והן עדיין 503; הקריאה של הספרייה מחזירה `null` ויורדת ללוג. **`stories`
⛔ אינו קלט ל-`unlocked`.**

⛔ **`stories.cefr_level` ⛔ אינה `senses.cefr_level`** (D-034) ו⛔ אינה `words.cefr_profile_band` —
היא העמודה של `0018_stories.sql`, שהערת העמודה שלה אומרת זאת במפורש.

⛔ **`senses.cefr_level` אינו נקרא, אינו נכתב ואין מיון לפיו** (D-034).

⚠️ **שתי תוספות לחוזה הצרכן, ⛔ שתיהן נמדדות ב-`components/TabBar.test.ts`:**

**26/27/27/26 מתוך 97/120/122/135** — מספר **בלתי-תלוי בסדר**. ⇒ השינוי ⛔ **אינו
מוסיף מפגש אחד**; הוא **מקדים 25** מהם (אחרי הסיפור השני: A1 ‏8⇢13 · A2 ‏9⇢16 ·

⛔ **בייצור (`NODE_ENV === 'production'`) הנתיב מחזיר 404 עירום ואינו מסגיר
את קיומו** — אין הבדל בין "לא הוגדר" ל"הוגדר אבל ייצור". ⛔ הנתיב **אינו יוצר**
משתמש (`signUp`) — הוא מנסה `signInWithPassword` בלבד, על משתמש שנוצר **ביד**
פעם אחת ב-Supabase (`plan/03-for-roy.md` פריט 36).

| מצב | תשובה |
|---|---|
| שער סגור (כל סיבה) | **404**, גוף ריק. ⛔ אין JSON, אין קוד, אין הודעה |
| שער פתוח · אין env של Supabase | **503** `{ "ok": false, "code": "unavailable" }` |
| שער פתוח · `signInWithPassword` נכשל | **401** `{ "ok": false, "code": "dev_user_missing", "message": "<עברית שנוקבת בצעד הידני>" }` |
| שער פתוח · הצלחה | **302** ל-`/` עם עוגיית הסשן |

⚠️ **הרצה חיה מול Supabase לא בוצעה בטיק שנבנה בו** — הנתיב נבדק בסריקת מקור
(סדר ההפעלות, זליגת סיבה, איסור `signUp`/`service-role`) ואומת ש-`npm run
build` מקמפל אותו תחת `NODE_ENV=production`; חיבור בפועל דורש `.env.local`
ומשתמש אמיתי שאין לסוכן גישה אליהם.

## אימות מובייל ו-PWA — `npm run check:mobile`

חוזה ה-API אינו הדבר היחיד שנאכף אוטומטית. `scripts/verify-mobile.mjs` מריץ את
הערבויות של מדורים 3.2 ו-3.3 מול בילד הפרודקשן, ומחזיר קוד יציאה 1 על כל הפרה:

* אפס גלילה אופקית ב-320px · 375px · 414px (MF-4)
* כל יעד מגע ≥ 44×44px, בכל מסך ובכל רוחב (MF-2)
* `dir="rtl"` ו-`lang="he"` נשמרים בכל נתיב — כולל 404 ומסכי שגיאה (MF-3)
* הפעולה הראשית יושבת בחצי המסך התחתון (MF-5)
* manifest תקין: `standalone` · `theme_color` · אייקוני 192/512 · maskable · כולם נגישים (PW-1)
* ה-Service Worker נרשם, מופעל, ומגיש מסך עברי אמיתי במצב אופליין (PW-2)
* הצעת ההתקנה **אינה** מוצגת בטעינת הדף (תוכנית UX של T-001)

הרצה: `npm run build && npm start` ואז `npm run check:mobile`.
בסביבה שבה Chromium מותקן מראש: `CHROME_PATH=/path/to/chrome npm run check:mobile`.

**למה זה קיים:** Lighthouse 13 הסיר את קטגוריית ה-PWA ואת audit ה-tap-targets,
כך שמדד ההצלחה של T-001 לא ניתן היה למדוד דרכו. הסקריפט מודד את מה שהובטח בפועל.

## Not an endpoint: `npm run measure:coverage`

A local batch script (`scripts/measure-coverage.mjs`), never reachable over HTTP
and never called at request time. It reads `data/` and writes
`docs/coverage-report.md`. Documented here so a future reader looking for where
coverage numbers come from does not go hunting for a route.
